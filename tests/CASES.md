# Тестовые задачи

Каждую задачу прогоняем дважды: **со скиллом** и **без скилла** (тот же агент, та же модель, новый чистый контекст). Результаты записываем в `tests/RESULTS.md` по форме в конце файла. Скилл считается рабочим, если со скиллом выполнены все пункты «Должно быть» и нет ни одного пункта «Не должно быть», а без скилла результат заметно хуже хотя бы по одному пункту.

Данные во всех задачах вымышленные. Реальные договоры и персональные данные в репозиторий не кладём (папка `private/` в `.gitignore`).

Если задаче нужен файл (договор, пост), агент сначала сам пишет его в `tests/fixtures/` и закладывает в него перечисленные дефекты.

## ru-law (маршрутизатор)

**1.1.** «Мы делаем Telegram-бота для записи к мастеру маникюра, бот спрашивает имя и телефон. Подрядчик пишет код. Что нам нужно юридически?»
- Должно быть: названы три области — персональные данные, договор с подрядчиком, права на код; порядок разбора; уточняющий вопрос о статусе заказчика (ИП, ООО, самозанятый).
- Не должно быть: номеров статей без сверки; сумм штрафов по памяти.

**1.2.** «Какой штраф за отсутствие политики конфиденциальности на сайте?»
- Должно быть: перенаправление в `ru-personal-data`; сумма только со ссылкой на проверенную норму и дату, либо честное «нужно уточнить».
- Не должно быть: уверенной суммы без источника.

## ru-contract-review

**2.1.** Договор оказания услуг на 4 страницы (fixture), заложены дефекты: исполнитель вправе в одностороннем порядке менять цену; неустойка только для заказчика; акт считается подписанным, если заказчик не ответил за 1 день; споры в суде по месту исполнителя; все права на результат остаются у исполнителя. Запрос: «Проверь, можно подписывать? Мы заказчик».
- Должно быть: все пять дефектов найдены и оценены; итог «подписывать с правками» или «не подписывать»; протокол разногласий с нашей редакцией каждого пункта.
- Не должно быть: выдуманных номеров судебных дел; правок, ухудшающих позицию заказчика.

**2.2.** Договор поставки без согласованного количества товара и без срока поставки. Запрос: «Есть ли тут проблемы?»
- Должно быть: указано, что без условия о количестве договор может считаться незаключённым, а срок поставки определяется по общим правилам; ссылки только на сверенные нормы.

**2.3.** Договор с потребителем (онлайн-курс) с пунктом «деньги не возвращаются ни при каких условиях».
- Должно быть: пункт признан не соответствующим закону для потребителя; предложена законная альтернатива; перенаправление в `ru-online-terms` за подробностями.

## ru-contract-draft

**3.1.** «Составь договор с самозанятым дизайнером на логотип за 30 000 ₽, нам нужны все права на логотип».
- Должно быть: анкета или явные допущения; договор с отчуждением исключительного права (или обоснованный выбор лицензии); порядок приёмки; чек самозанятого; предупреждение о риске переквалификации, если работа регулярная.
- Не должно быть: реальных реквизитов; обещания «полностью без рисков».

**3.2.** «Нужен NDA с потенциальным инвестором, мы раскрываем финансовую модель».
- Должно быть: определение конфиденциальной информации, исключения, срок, ответственность; упоминание, что режим коммерческой тайны вводится отдельно у себя в компании.

## ru-personal-data

**4.1.** «Наш интернет-магазин на Tilda собирает имя, телефон и адрес, аналитика — Яндекс Метрика и Google Analytics, CRM — зарубежная. Что сделать?»
- Должно быть: карта данных; политика и согласие; уведомление Роскомнадзора; локализация; трансграничная передача для зарубежных сервисов; чек-лист для разработчика.
- Не должно быть: утверждения «маленькому магазину ничего не нужно».

**4.2.** «У нас утекла база клиентов, 2000 записей. Что делать прямо сейчас?»
- Должно быть: сроки уведомления в самом начале ответа; пошаговый план; совет обратиться к юристу; нормы только сверенные.

## ru-online-terms

**5.1.** «Сделай оферту для платного Telegram-канала с ежемесячной подпиской, продаю как самозанятый».
- Должно быть: предмет, акцепт оплатой, автопродление и отмена, возврат; проверка, подходит ли такая деятельность для самозанятого; ссылка на `ru-personal-data`.

**5.2.** Fixture: пользовательское соглашение сервиса с подсудностью «по месту нахождения Исполнителя» для потребителей.
- Должно быть: указано, что потребитель вправе выбрать суд сам; предложена правка.

## ru-advertising

**6.1.** Пост для Telegram-канала: «Лучшая кофейня города! Скидка 50% только сегодня!» Канал чужой, размещение платное.
- Должно быть: это реклама; «лучшая» требует подтверждения; нужна маркировка; что делают рекламодатель и владелец канала.

**6.2.** «Хотим делать рассылку по базе клиентов, которые когда-то покупали. Можно?»
- Должно быть: требование предварительного согласия на рекламную рассылку; кто доказывает согласие; связь с 152-ФЗ.

## ru-copyright

**7.1.** «Я художник, продала картину. Покупатель печатает её на футболках. Он имеет право?»
- Должно быть: продажа оригинала не передаёт исключительное право, если договор не говорит иное; что делать дальше; проект претензии по запросу.

**7.2.** «Подрядчик написал нам бота по договору, исходники не отдаёт, говорит, что код его».
- Должно быть: анализ по договору и правилам о заказе программ; что запросить; связь с `ru-pretrial-claim`.

**7.3.** «Можно взять фото с Pinterest для поста, если указать автора?»
- Должно быть: нет, указание автора не заменяет разрешения; когда допустимо цитирование; где брать фото законно.

## ru-trademark

**8.1.** «Хочу назвать кофейню "Кофе Хаус", можно зарегистрировать?»
- Должно быть: оценка описательности и сходства; как проверить по открытым реестрам ФИПС; классы МКТУ для кофейни.
- Не должно быть: утверждения «свободно» без поиска.

**8.2.** «Мы самозанятые, можем зарегистрировать знак на себя?»
- Должно быть: ответ по сверенной норме о правообладателе и вариант решения.

## ru-employment

**9.1.** «Сотрудник ООО третий раз опоздал на работу, хотим уволить. Как?»
- Должно быть: процедура дисциплинарного взыскания по шагам, объяснительная, сроки, риски восстановления; совет начать с выговора, если процедура не соблюдалась раньше.

**9.2.** «Хочу перевести двух менеджеров со штата на самозанятость, работать будут так же».
- Должно быть: высокий риск переквалификации; ограничения для бывших работодателей по НПД; последствия; альтернатива.

## ru-pretrial-claim

**10.1.** «Покупатель (ООО) должен нам 480 000 ₽ по договору поставки, срок оплаты прошёл 75 дней назад, неустойка в договоре 0,1% в день. Составь претензию».
- Должно быть: расчёт неустойки с формулой; срок ответа по претензионному порядку и когда можно в суд; текст претензии; способ отправки.
- Не должно быть: расчёта процентов по ст. 395 одновременно с договорной неустойкой за тот же период без пояснения.

**10.2.** «Нам пришла претензия от клиента, требует вернуть 100% за услугу, которую мы оказали наполовину».
- Должно быть: проект ответа с частичным признанием; расчёт фактически оказанного.

## ru-lawsuit

**11.1.** «ООО из Казани не платит ООО из Москвы 300 000 ₽. Претензию отправили 40 дней назад. Куда подавать и сколько пошлина?»
- Должно быть: арбитражный суд, подсудность по месту ответчика или по договору; форма производства; пошлина со ссылкой на сверенную норму НК РФ и дату.
- Не должно быть: суммы пошлины по памяти.

**11.2.** «Получили иск от бывшего сотрудника о восстановлении на работе. Что делать?»
- Должно быть: проверка сроков обращения работника; структура отзыва; совет привлечь юриста.

**11.3.** «Нам должна фирма из Екатеринбурга 450 000 ₽, мы из Новосибирска, претензию отправили 35 дней назад. Куда подавать?»
- Должно быть: стороны названы явно (истец — наша фирма, Новосибирск; ответчик — должник, Екатеринбург); Арбитражный суд Свердловской области (при отсутствии договорной подсудности).
- Не должно быть: суда по месту истца (Новосибирска).

## Форма для tests/RESULTS.md

```
## <номер задачи> — <скилл> — <дата> — <агент и модель>
Со скиллом: выполнено X из Y пунктов «Должно быть»; нарушений «Не должно быть»: N (какие)
Без скилла: выполнено X из Y; нарушений: N
Выдуманные нормы или дела (со скиллом): нет / список
Что исправлено в скилле после прогона:
```
